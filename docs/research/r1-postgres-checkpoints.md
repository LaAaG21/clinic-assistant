# R1: PostgreSQL checkpoint persistence

- **Issue:** #3 · **Owner:** Louai1999 · **Date:** 2026-11-02 · **Status:** experiment done; recommendation **Proposed** (not yet agreed)
- **Open:** comparison with #4 and the spike share-out have not happened yet; the ADR in `docs/adr/` is written only after team agreement.
- **Experiment:** [`experiments/r1_checkpoints/`](../../experiments/r1_checkpoints/)

## Question

How do we keep each conversation's LangGraph state under its own thread ID so that it survives a container restart, using PostgreSQL as the only database?

## Options compared

| Option | Survives restart? | Fits our rules? | Notes |
|---|---|---|---|
| `InMemorySaver` (`MemorySaver`) | No, lives in process memory | Spike only | Lost on every restart. |
| JSON files per session (our chat-sessions exercise) | Only with a volume | No | Hand-written, not integrated with LangGraph, a second storage. |
| `SqliteSaver` | Yes | **No** | SQLite is forbidden. |
| **`PostgresSaver`** (`langgraph-checkpoint-postgres`) | **Yes** | **Yes** | Official, uses psycopg 3, plain SQL, no ORM. **Tested here.** |
| `AsyncPostgresSaver` (same package) | Yes | Yes | Same storage for async code (FastAPI). Not tested. |

## Experiment

One-node graph (`reply`) whose state is `messages` (appended) and `turns`. A fake LLM returns a fixed reply per turn, and the turn number comes **only from the restored state**: if the state were lost, turn 3 would get the turn-1 reply. No API key is used.

## Reproduction

```bash
cd experiments/r1_checkpoints
cp .env.example .env            # then set POSTGRES_PASSWORD
docker compose up -d --build --wait
docker compose exec spike python spike.py send patient-42 "When is Dr. Salma free on Thursday?"
docker compose exec spike python spike.py send patient-42 "Book the 10:00 slot"
docker compose exec spike python spike.py show patient-42
docker compose down             # removes both containers, keeps the named volume
docker compose up -d --wait
docker compose exec spike python spike.py show patient-42
docker compose exec spike python spike.py send patient-42 "Thanks"
docker compose exec spike python spike.py show patient-99
```

## Observed results (thread `patient-42`)

| Moment | spike container | `turns` | Last bot reply |
|---|---|---|---|
| Before restart | `2cc26a24e35b` | 2 | "Noted. Anything else I can help with?" |
| After `down` + `up` | `8b5a96bbe4c1` (new) | 2, all 4 messages intact | same |
| Next message "Thanks" | `8b5a96bbe4c1` | 3 | "You're welcome. Have a good day!" (turn-3 reply, so state was restored) |

- `patient-99` returned `turns=0`: threads are isolated.
- `setup()` created `checkpoints`, `checkpoint_blobs`, `checkpoint_writes`, `checkpoint_migrations`.
- 9 checkpoint rows for 3 messages: one checkpoint per graph step, which is what lets a graph pause mid-run (#4).

## Automated tests

Run inside the `spike` container against the real PostgreSQL service (no model key):

```bash
docker compose up -d --build --wait
docker compose exec spike pytest -v
```

| Test | What it proves |
|---|---|
| `test_fake_llm.py` (3 tests) | Fixed reply per turn, last reply repeats, same turn gives the same reply. |
| `test_same_thread_is_restored_by_a_new_saver_and_graph` | State written through one connection is read by a **new** saver and **new** graph (`turns=2`, 4 messages), and the next message becomes turn 3 with the turn-3 reply. |
| `test_a_different_thread_is_isolated` | A second thread ID is empty while the first holds state. |

Result (2026-11-02): `5 passed in 0.84s` on Python 3.12.16, pytest 9.2.0. Each test uses a random `test-<uuid>` thread ID, and database tests fail (not skip) when `DATABASE_URL` is missing. The container restart above remains the evidence for container/volume behaviour; the tests cover reconnection in code.

## Recommendation (Proposed)

1. Use `PostgresSaver` (or `AsyncPostgresSaver` if the API is async) on the same PostgreSQL database as the rest of the app.
2. **`thread_id` = `conversation_id`**: generated by the server as a random UUID, never chosen by the client.
3. Call `setup()` once at application start-up; it is idempotent and creates/migrates its own tables, so no manual SQL is needed.
4. Use one checkpointer design for both R1 and R2: interrupt/resume (#4) needs this same checkpointer and thread ID.

## Risks

| Risk | Mitigation |
|---|---|
| Our own connection or pool must match `from_conn_string`: `autocommit=True`, `row_factory=dict_row`, `prepare_threshold=0`. | Build the pool with these settings; cover with an integration test. |
| Rows grow with every step (3 per message here). | Accept for v1; note retention/cleanup as a later item. |
| Changing the state schema between releases can break old threads. | Add fields as optional; avoid renaming keys. |
| Sync saver inside async FastAPI handlers blocks the event loop. | Decide sync vs async in the API design (#6). |
| Two messages on the same thread at once were not tested. | Test in production integration. |
| Message history grows forever; only a bounded window may go to the model (FR-1). | Trim in the node before calling the model; keep full history in state. |

## Learning check

*Why must the same thread ID and durable database be used after a restart?*
The thread ID is the key the checkpointer uses to find a conversation's saved state: a different ID starts an empty conversation. The database must be durable (PostgreSQL on a named volume) because an in-memory saver loses everything when the process or container stops, so there would be nothing to load.
